# GOWAYY setup

## Local development (customer web + development API)

```bash
npm install
npm run dev          # dev API on :8787, Vite web on :5173
npm run verify       # typecheck (web + mobile), unit, integration, SQL, Edge, web build
```

The development API (`apps/dev-api`) is a real Node HTTP service with JSON persistence,
server-side pricing, idempotency, availability, refunds, notifications, partner gating,
dispatch and audit log. It is **not** a mock UI. The web app proxies `/api` to it.
`apps/dev-api/data/db.json` is gitignored.

Registration uses a **clearly labelled demo OTP adapter**: it never claims to send email
and never pretends demo verification is real verification. Password hashing, sessions
and rate limits run on the server. Payments are sandbox-only; capture requires a
server-verified event, never a client-side success signal.

## Android (Expo SDK 58)

```bash
cd apps/mobile
npm install --legacy-peer-deps
cp .env.example .env        # set an absolute LAN/IP or HTTPS API URL
npm run typecheck           # TypeScript strict
npm run start               # Expo dev server
npm run web                 # Expo web preview
npm run build:android:dev   # EAS development APK (requires EAS account/project)
npm run build:android:prod  # EAS production AAB
```

`apps/mobile/app.json` defines the `gowayy://` scheme, `gowayy.app` App Links,
`app.gowayy.customer` package, adaptive/monochrome icons, splash, and location +
notification permissions. `eas.json` defines `development`/`preview` APK profiles and a
`production` app-bundle profile. Run `eas init` once to add a real `projectId` under
`expo.extra.eas.projectId` before building; none is fabricated in this repository.

On a physical device `localhost` is not the API. Set
`EXPO_PUBLIC_GOWAYY_API_BASE_URL` to a reachable origin and
`EXPO_PUBLIC_GOWAYY_ASSET_BASE_URL` to the host serving `apps/web/public/`. Without an
asset base the app shows the designed unavailable state for photographs rather than a
substitute image.

Verified in this workspace (2026-11-04): mobile `tsc --noEmit` clean,
`expo export --platform web` produced 36 web bundles, and
`expo export --platform android` produced a 5.2 MB Hermes bundle. No EAS build,
APK/AAB, Supabase deployment or on-device test has been run.

## Supabase backend (production target)

Migrations live in `supabase/migrations/202611040001` … `202611040010`, seed in
`supabase/seed/0001_catalog.sql` (generated by `npm run seed:supabase`). Apply with the
Supabase CLI:

```bash
supabase link --project-ref YOUR_REF
supabase db push
supabase functions deploy gowayy-api
supabase functions deploy payment-webhook
```

Set Edge Function secrets (server-side only, never in a client bundle):

| Secret | Purpose |
| --- | --- |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | project URL and public anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | server-only Auth admin + privileged RPCs |
| `GOWAYY_PAYMENT_WEBHOOK_SECRET` | HMAC-SHA256 verification of payment webhooks |
| `GOWAYY_EMAIL_PROVIDER_URL` | real email OTP provider (optional; without it the gateway fails honestly instead of claiming email was sent) |

`supabase/config.toml` disables gateway `verify_jwt` because `gowayy-api` verifies the
caller's JWT itself against `/auth/v1/user`, then forwards that JWT to PostgREST/RPC so
`auth.uid()` is the verified account. Row Level Security is enabled on every public
table. `payment-webhook` verifies the signature before calling the service-role-only
`rpc_webhook_capture`.

To select the hosted backend in web: `VITE_GOWAYY_BACKEND=supabase`,
`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Mobile equivalents use `EXPO_PUBLIC_*`.

## PostGIS

`001_foundation.sql` guards extension creation and `010_read_models.sql` calls
`gowayy_attach_geo()` again. Geography columns and GiST indexes are created only when
`postgis` is available. PGlite/PostgreSQL 17.5 verification in this workspace confirmed
the guard returns a boolean; it did **not** confirm a PostGIS-enabled run.
