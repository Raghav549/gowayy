# GOWAYY setup

## Local development (customer web + development API)

```bash
npm install
npm run dev:all      # dev API :8787, customer :5173, partner :5174, admin :5175
npm run verify       # typecheck (web + mobile), unit, integration, SQL, Edge, web build
```

The root install covers web/API work. Before `npm run verify` or any mobile typecheck,
install each independent Expo app with `npm ci --prefix apps/gowayy-customer/mobile`,
`npm ci --prefix apps/gowayy-partner/mobile`, and `npm ci --prefix apps/gowayy-admin/mobile`.

The development API (`apps/dev-api`) is a real Node HTTP service with JSON persistence,
server-side pricing, idempotency, availability, refunds, notifications, partner gating,
dispatch and audit log. It is **not** a mock UI. The web app proxies `/api` to it.
`apps/dev-api/data/db.json` is gitignored.

Registration uses a **clearly labelled demo OTP adapter**: it never claims to send email
and never pretends demo verification is real verification. Password hashing, sessions
and rate limits run on the server. Payments are sandbox-only; capture requires a
server-verified event, never a client-side success signal.

## Android (Expo SDK 57 + native Gradle)

```bash
npm ci --prefix apps/gowayy-customer/mobile
cd apps/gowayy-customer/mobile
npm run typecheck
npm run start
```

Production and PR APKs are built by `.github/workflows/mobile-build.yml` using Expo's clean native prebuild and Gradle `assembleRelease` / `assembleDebug` tasks. No EAS account, Expo token, or EAS build service is used. The workflow checks application IDs and version data, APK signatures and archive integrity, then publishes per-app artifacts. See `docs/DEPLOYMENT.md` for signing-secret setup and release/update behavior.

Package IDs are `app.gowayy.customer`, `app.gowayy.partner`, and `app.gowayy.admin`. The native system splash uses `assets/branding/splash-mark.png` (inverse white mark) on the purple `#421080` background; a reduced-motion-aware animated symbol-only launch transition follows. Each app's App updates screen checks its own GitHub Release, shows notes and transfer progress, verifies the downloaded package, and opens Android's installer. Android requires the user to approve unknown-source installs and confirm the update; installation is not silent.

For local native Gradle builds use Java 17 and the Android SDK/platform/build tools from the workflow. On a physical device `localhost` is not the API. Set `EXPO_PUBLIC_GOWAYY_API_BASE_URL` to a reachable origin and `EXPO_PUBLIC_GOWAYY_ASSET_BASE_URL` to the host serving the customer's public assets. Without an asset base the app shows the designed unavailable state for photographs rather than a substitute image.

## Supabase backend (production target)

Migrations live in `supabase/migrations/202611040001` … `202611040023`, seed in
`supabase/seed/0001_catalog.sql` (generated by `npm run seed:supabase`). Apply with the
Supabase CLI:

```bash
supabase link --project-ref YOUR_REF
supabase db push
supabase functions deploy gowayy-api
supabase functions deploy payment-webhook
supabase functions deploy push-dispatcher  # cron/webhook worker for durable push
```

Set Edge Function secrets (server-side only, never in a client bundle):

| Secret | Purpose |
| --- | --- |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | project URL and public anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | server-only Auth admin + privileged RPCs |
| `GOWAYY_PAYMENT_WEBHOOK_SECRET` | HMAC-SHA256 verification of payment webhooks |
| `GOWAYY_PAYMENT_PROVIDER` | `razorpay` for live orchestration; `unconfigured` disables online capture |
| `GOWAYY_RAZORPAY_KEY_ID`, `GOWAYY_RAZORPAY_KEY_SECRET` | server-side Razorpay order/refund API credentials; only the key ID is returned for checkout |
| `GOWAYY_EMAIL_PROVIDER_URL` | real email OTP provider (optional; without it the gateway fails honestly instead of claiming email was sent) |
| `GOWAYY_EXPO_PUSH_ENABLED` | `true` to enable Expo push dispatch; without it the gateway reports `expoEnabled: false` and dispatch retries honestly |
| `GOWAYY_EXPO_ACCESS_TOKEN` | optional Expo access token for authenticated Expo push |
| `GOWAYY_VAPID_SUBJECT`, `GOWAYY_VAPID_PUBLIC_KEY`, `GOWAYY_VAPID_PRIVATE_KEY` | Web Push VAPID credentials (`npx web-push generate-vapid-keys`); without them browser push retries honestly and `pushConfig` omits the public key |
| `GOWAYY_PUSH_DISPATCH_SECRET` | bearer for `push-dispatcher` (`x-gowayy-push-key` or `Authorization: Bearer`); required to claim deliveries |
| `SUPABASE_AUTH_SMS` | configure Supabase Auth SMS (Twilio) in the Supabase dashboard; phone OTP uses `supabase.auth.signInWithOtp` + `verifyOtp` — no custom SMS code is needed |
| `VITE_GEOCODING_REVERSE_URL` | optional browser reverse-geocode endpoint with `{lat}`, `{lng}`, `{key}` placeholders; without it the customer web falls back to offline nearest-place (never invents a location) |
| `VITE_GEOCODING_API_KEY` | optional private key for the reverse-geocode endpoint; never commit a real key |

For the customer web, location permission is requested only on explicit user action. The UI explains why location is needed (ranking nearby services, PIN-code checks, cab/parcel pickup), handles denied permissions, GPS disabled, timeouts and retry, and shows the last saved GPS/manual choice. Without permission the app still works by choosing a destination manually. See `apps/gowayy-customer/web/src/lib/location.ts`. Mobile uses `expo-location` with the same explanatory flow (`apps/gowayy-customer/mobile/src/lib/location.ts`); background tracking is not enabled.

`supabase/config.toml` disables gateway `verify_jwt` because `gowayy-api` verifies the
caller's JWT itself against `/auth/v1/user`, then forwards that JWT to PostgREST/RPC so
`auth.uid()` is the verified account. Row Level Security is enabled on every public
table. `payment-webhook` verifies the signature before calling the service-role-only
`rpc_webhook_capture`.

For Razorpay, set the Edge secrets without committing their values:

```bash
supabase secrets set \
  GOWAYY_PAYMENT_PROVIDER=razorpay \
  GOWAYY_RAZORPAY_KEY_ID="$GOWAYY_RAZORPAY_KEY_ID" \
  GOWAYY_RAZORPAY_KEY_SECRET="$GOWAYY_RAZORPAY_KEY_SECRET" \
  GOWAYY_PAYMENT_WEBHOOK_SECRET="$GOWAYY_PAYMENT_WEBHOOK_SECRET"
```

Configure Razorpay to POST `payment.captured`, `payment.failed`,
`refund.processed`, and `refund.failed` to
`https://YOUR_PROJECT_REF.supabase.co/functions/v1/payment-webhook`, using the same
webhook secret. The function verifies `x-razorpay-signature`; a browser redirect or
success callback never captures payment. Live charges/refunds remain unverified until
this is run with real provider credentials.

To select the hosted backend in web: `VITE_GOWAYY_BACKEND=supabase`,
`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Mobile equivalents use `EXPO_PUBLIC_*`.

## Initial Customer, Partner and Admin accounts

Run the server-side provisioner only after migrations are applied. It uses the Supabase
Auth Admin API, assigns `customer`, `seller` and `admin` roles, and verifies a real
password session for each account. It never writes credentials or tokens to disk.
Existing users are found rather than duplicated; their passwords are not reset.

Set secrets interactively in your shell/secret manager (do not paste them into source or
commit a `.env` file), then run:

```bash
export SUPABASE_URL='https://YOUR_PROJECT_REF.supabase.co'
export SUPABASE_ANON_KEY='YOUR_PUBLIC_ANON_KEY'
export SUPABASE_SERVICE_ROLE_KEY='YOUR_SERVER_ONLY_SERVICE_ROLE_KEY'
export GOWAYY_CUSTOMER_EMAIL='customer@your-domain.example'
export GOWAYY_PARTNER_EMAIL='partner@your-domain.example'
export GOWAYY_ADMIN_EMAIL='admin@your-domain.example'
read -rsp 'Customer password: ' GOWAYY_CUSTOMER_PASSWORD; echo; export GOWAYY_CUSTOMER_PASSWORD
read -rsp 'Partner password: ' GOWAYY_PARTNER_PASSWORD; echo; export GOWAYY_PARTNER_PASSWORD
read -rsp 'Admin password: ' GOWAYY_ADMIN_PASSWORD; echo; export GOWAYY_ADMIN_PASSWORD
npm run provision:owners
```

Each password must be at least 12 characters and contain upper/lowercase letters, a
number and a symbol. Optional `GOWAYY_<CUSTOMER|PARTNER|ADMIN>_FIRST_NAME` and
`..._LAST_NAME` variables set profile names. The script has mocked API-contract unit
tests, but a real account is confirmed only when the script prints `OK` against your
Supabase project. Never use a publicly known default Admin password.

## PostGIS

`001_foundation.sql` guards extension creation and `010_read_models.sql` calls
`gowayy_attach_geo()` again. Geography columns and GiST indexes are created only when
`postgis` is available. PGlite/PostgreSQL 17.5 verification in this workspace confirmed
the guard returns a boolean; it did **not** confirm a PostGIS-enabled run.
